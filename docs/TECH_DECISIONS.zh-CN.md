## D01 系统定位:研究报告助手,不做评级与回测

**状态** 已采纳

**问题**
系统输出"带出处的研究报告",还是同时输出"看多/中性/看空"评级。

**候选方案**

| 方案 | 优点 | 缺点 |
|---|---|---|
| 报告 + 评级 + 回测验证 | 判断有客观对错标准,可自动产生负样本 | 回测须处理前视偏差,而模型训练数据本身包含截止日之后的信息,只能在模型训练截止日之后的时点评测,样本获取慢;命中率需要数百样本才有统计意义;需补量化专业知识 |
| 报告 + 评级,不回测 | 输出看起来更"完整" | 评级对错无法检验,违背"每项技术必须可验证"的原则 |
| **只输出带出处的报告** | 质量可用事实类评测与引用核验度量;范围可控 | 不提供投资判断 |

**决策** 只输出带出处的研究报告,不输出评级,不做回测。护栏层拒绝买卖建议与价格预测类请求。

**理由**
- 没有回测,评级的对错无法验证;与其输出无法验证的东西,不如不输出。
- 报告的可靠性(数值准确、引用真实、不编造)本身就是金融场景最难、也最有价值的部分。

**代价** 失去"后验结果"这一自动化负样本来源;优化飞轮的信号只能来自 Critic 拦截记录、评测低分与用户反馈。

**改变决策的条件** 明确需要验证判断质量,且评测时点可以全部放在所用模型的训练截止日之后。

## D02 工作流优先与初始角色集

**状态** 已采纳

**问题**
系统需要几个 Agent,哪些环节由模型自主决策。

**候选方案**

| 方案 | 优点 | 缺点 |
|---|---|---|
| 按分析维度设多个专职 Agent(财务、技术、情绪、宏观、多空辩论等) | 分工直观,演示效果好 | 每个角色都增加成本与评测负担;多数维度缺少数据源或不在范围内;难以说明每个角色的贡献 |
| 一个 Agent 持有全部工具 | 实现最简单 | 复杂问题上下文膨胀,难以并行 |
| **工作流为主,只在必要处用 Agent** | 成本与行为可预测,便于评测 | 需要预先设计流程,灵活性受限 |

**决策** 初始角色集 5 个:Router、Orchestrator、Analyst、Synthesizer、Critic。其中只有 Analyst 是 Agent(在循环中自主选择工具),其余是图中固定位置的模型调用。Analyst 是同一定义的多个并行实例,按"标的 × 研究维度"拆分。简单查数问题走不经过 Orchestrator 的固定工作流。

**理由**
- 自主性越高,成本、延迟与出错面越大,评测也越难。只有路径无法预先确定的环节(某个子问题需要查哪些数据、查几次)才交给模型。
- 研究维度通过子任务描述区分即可,不需要为每个维度单独维护 prompt、工具集与评测。

**代价** 多维度深度分析的能力受限于单一 Analyst 定义的通用性。

**改变决策的条件** 增量实验(实验 B)显示某个维度在现有设计下存在明确缺口,且具备该维度的数据源。

**验证** 实验 B:逐个加入扩展候选角色,指标提升超过重复运行的标准差才保留。

## D03 编排模式:单 Agent 与多 Agent

**状态** 待实测

**问题**
复杂问题(多维度研究、多标的对比)用一个 Agent 处理,还是拆成多个并行子任务。

**候选方案**

| 方案 | 优点 | 缺点 |
|---|---|---|
| 单 Agent 循环 | 实现简单、token 消耗低、无汇总损失 | 材料多时上下文超出预算;串行执行耗时长 |
| **编排者 + 并行 Analyst** | 各子任务上下文隔离;并行降低耗时 | token 消耗成倍增加;汇总环节可能丢信息 |

**决策(假设)** 复杂问题采用编排者 + 并行 Analyst,简单问题走固定工作流。

**理由** 一次研究所需材料(多期财报、多个标的)远超单次上下文预算,子任务隔离是控制上下文的主要手段。

**代价** 成本上升;需要 Synthesizer 与 Critic 处理汇总质量。

**改变决策的条件** 实验 A 显示多 Agent 的质量提升在标准差范围内,或成本增幅与质量提升不相称。

**验证** 实验 A:同一评测集、同检索参数、关闭结果缓存,每题运行 3 次,对比质量指标、token、成本与延迟。

**对比数据** 待实测。

## D04 编排框架:LangGraph

**状态** 已采纳

**问题**
Agent 流程用什么框架实现。

**候选方案**

| 方案 | 优点 | 缺点 |
|---|---|---|
| 自研循环与状态机 | 完全可控,依赖少 | 检查点、中断恢复、并行分支都要自己实现 |
| **LangGraph** | 显式的图与状态;自带 Postgres 检查点、中断(人工审批)与恢复;模型无关 | 引入框架抽象与版本演进风险;检查点使用其自有连接 |
| Claude Agent SDK | Agent 循环、工具、子 Agent 能力完整 | 只能使用 Claude 模型,国内部署时不可用;偏向自主 Agent,不适合显式流程控制 |
| PydanticAI | 类型安全,模型无关 | 持久化执行与人工审批需要更多自行实现 |

**决策** 使用 LangGraph 实现编排图;模型调用不通过框架,而是走自己的 llm 模块。

**理由**
- 本系统以显式工作流为主(D02),LangGraph 的"图 + 状态 + 条件边"与之一致。
- 检查点、中断与恢复正是 Durable Execution(D19)与人工审批所需要的。
- 模型调用走自己的 llm 模块,使档位映射、成本记账、重试预算不依赖框架,也降低了框架锁定。

**代价** 框架升级可能带来破坏性变更;检查点与业务表不在同一事务(见 D19)。

**改变决策的条件** 框架的检查点或中断机制无法满足恢复语义要求,或升级成本持续过高。

## D05 服务边界:模块化单体 + worker + sandbox-runner

**状态** 已采纳

**问题**
系统拆成几个独立部署的服务。

**候选方案**

| 方案 | 优点 | 缺点 |
|---|---|---|
| 单进程单体 | 部署最简单 | 分钟级任务阻塞请求处理;生成代码与主服务同进程,无安全边界 |
| 按模块拆微服务(检索、数据、模型各一个服务) | 独立扩缩 | 网络调用、部署与一致性成本高,单人维护负担大 |
| **模块化单体 + worker + sandbox-runner** | 只在有明确理由处拆分 | 模块边界靠约定与静态检查维护 |

**决策** api(模块化单体)、worker、sandbox-runner、frontend 四个部署单元。拆分判据:安全边界、资源与生命周期差异、独立发布节奏、独立扩容需求,至少满足一条才拆。

**理由**
- sandbox-runner 执行模型生成的代码,需要容器级隔离。
- worker 执行分钟级任务,与短请求的进程模型和扩容维度不同。
- 检索、数据、模型等模块不满足任何一条判据,拆开只增加网络调用与运维成本。

**代价** 模块间依赖须靠 CI 的依赖方向检查维持。

**改变决策的条件** 某个模块出现独立扩容或独立发布需求。

## D06 存储:PostgreSQL + pgvector

**状态** 已采纳

**问题**
业务数据、向量、检查点、评测记录分别存在哪里。

**候选方案**

| 方案 | 优点 | 缺点 |
|---|---|---|
| **PostgreSQL + pgvector 一库** | 元数据过滤与向量检索在同一查询中完成;事务、备份、运维只有一套 | 超大规模下向量检索性能弱于专用库;过滤语义需要额外处理(D07) |
| PostgreSQL + 独立向量库(Milvus、Qdrant 等) | 大规模性能强,索引类型多 | 文档元数据要同步两份,存在一致性风险;多一个有状态服务 |
| FAISS 等嵌入式索引 | 单机性能高 | 无持久化与过滤能力,需自行封装 |

**决策** 使用 PostgreSQL + pgvector,检索实现依赖 `VectorStore` 抽象接口。

**理由**
- 检索强依赖元数据过滤(标的、时点、文档类型、权限),过滤条件与业务数据始终一致。
- 本系统的向量规模(数十家公司、数年报告)远在 pgvector 的适用范围内。

**代价** 带严格过滤条件的近似检索需要专门处理(D07)。

**改变决策的条件** 向量规模达到千万级,或检索延迟成为瓶颈且无法通过索引参数解决。`VectorStore` 抽象使切换局限于一个实现类。

## D07 带过滤条件的向量检索

**状态** 待实测

**问题**
pgvector 在 HNSW 等近似索引上,过滤发生在索引扫描之后:先按 `ef_search` 取回候选,再应用 WHERE 条件。过滤越严格(单一标的、某日期之前、特定文档类型),满足条件的候选越少,返回结果可能不足 k 条。

**候选方案**

| 方案 | 优点 | 缺点 |
|---|---|---|
| 调大 `ef_search` | 配置简单 | 所有查询都变慢,仍无法保证数量 |
| 迭代索引扫描(pgvector ≥ 0.8,`hnsw.iterative_scan`) | 候选不足时继续扫描 | 最坏情况延迟上升,需设扫描上限 |
| 按标的分区或建部分索引 | 索引只包含目标范围,召回稳定 | 分区与索引数量随标的增长 |
| 候选规模小时精确检索 | 结果精确 | 候选规模大时延迟不可接受 |

**决策(假设)** 默认启用迭代索引扫描;单一标的且候选块数低于阈值时走精确检索;每次检索记录返回条数,不足 k 条计入指标。

**验证** 检索评测按"过滤严格程度"分层统计 Recall@k 与延迟,对比上述方案。

**对比数据** 待实测。

## D08 关键词检索与中文分词

**状态** 待实测

**问题**
关键词检索用于精确匹配科目名、股票代码、专有名词。两个事实决定了它不能直接使用 PostgreSQL 默认配置:默认解析器按空格与标点切词,一整句中文会成为一个词元;自带的 `ts_rank` 基于词频,不是 BM25,没有词频饱和与文档长度归一。

**候选方案**

| 方案 | 优点 | 缺点 |
|---|---|---|
| `ts_rank` + 中文分词扩展(zhparser 或 pg_jieba) | 库内完成,组件少 | 排序质量弱于 BM25;需要自定义数据库镜像 |
| 支持 BM25 的 PostgreSQL 扩展 | 库内完成且为 BM25 | 需评估其中文分词支持、版本兼容与部署成本 |
| 应用层 BM25(jieba 分词 + 倒排索引) | 实现透明,便于调试 | 需自行维护索引与增量更新 |

**决策(假设)** 先用 `ts_rank` + 中文分词扩展建立基线,再与 BM25 方案对比。

**理由** 混合检索在融合阶段使用 RRF,只依赖排名而不依赖原始分数,打分算法的差异只影响关键词一路的排序。先用最少组件建立基线,再用数据判断是否值得引入额外组件。

**验证** 检索评测中单独统计关键词一路的 Recall@k,以及对混合检索最终结果的影响。

**对比数据** 待实测。

## D09 分块策略

**状态** 待实测

**问题**
年报是 200 至 300 页的 PDF,关键数据在表格中,表格常跨页并带合并单元格。分块决定了检索的粒度与上下文完整性。

**候选方案**

| 方案 | 优点 | 缺点 |
|---|---|---|
| 固定长度 + 重叠 | 实现最简单 | 切断表格与段落 |
| **按章节结构切分,表格整体保留** | 语义完整,表格可读 | 块大小不均;依赖版面解析质量 |
| 父子块(小块检索,返回所属大块) | 兼顾检索精度与上下文 | 实现与存储更复杂 |

**决策(假设)** 按章节结构切分,目标约 512 token、重叠 64 token;表格不跨块切分,超长表格按行分块并复制表头;每块附加"文档标题 + 章节 + 报告期"上下文前缀后再嵌入。

**理由** 脱离上下文的块无法区分公司与年份,而"找到了错误年份的相似段落"是本领域最主要的检索失败。

**验证** 三种策略各建一套索引,比较 factual 与 retrieval 评测集上的 Recall@5,并抽检表格单元格提取正确率。

**对比数据** 待实测。

## D10 检索链路:混合检索 + RRF + rerank

**状态** 待实测

**问题**
如何从全部块中找到真正支持答案的片段。

**候选方案**

| 方案 | 优点 | 缺点 |
|---|---|---|
| 纯向量检索 | 理解语义与同义表达 | 对数字、科目名、代码等精确匹配不敏感 |
| 纯关键词检索 | 精确匹配强 | 不理解同义表达 |
| 混合检索 + RRF | 两者互补;RRF 只用排名,无需调权重 | 两路召回,延迟增加 |
| **混合检索 + RRF + rerank** | 交叉编码器精排,精度最高 | 增加一次模型推理的延迟与成本 |

**决策(假设)** 元数据过滤(含 PIT 约束)→ 向量与关键词各取 50 → RRF(k=60)融合 → 对前 30 条 rerank → 返回前 8 条。

**理由** 投研问题同时包含语义表述("毛利率下降的原因")与精确实体("研发费用""300750"),单一检索方式各有盲区。

**验证** 实验 C:纯向量、混合、混合 + rerank 三档,比较 Recall@5、NDCG@10 与 P95 延迟。所有参数纳入 `config_hash`。

**对比数据** 待实测。

## D12 时点正确性:双时间轴数据模型

**状态** 已采纳

**问题**
财报有披露滞后,且可能事后修订。不区分"数据描述的期间"与"数据公开的时间",会把修订后的数字当作当时已知的数字,或把尚未披露的报告当作已知信息。

**候选方案**

| 方案 | 优点 | 缺点 |
|---|---|---|
| 只存最新值 | 简单 | 无法回答"截至某日可知的数据" |
| **双时间轴:事件时间 + 可知时间,保留修订版本** | 任意时点的查询结果可复现 | 表结构与查询更复杂 |

**决策** 财务事实记录 `period_end`(事件时间)与 `known_at`(可知时间),同一期间保留多个修订版本;所有数据查询必须传入 `as_of`,无默认值;`as_of` 由框架注入,不由模型填写;检索层强制拼接 `published_at <= as_of_date`;退市标的保留在库中。

**理由**
- 研究报告必须说明"基于截至何时的信息",否则结论不可复核。
- 由框架注入并在数据层强制,保证约束不依赖调用方(包括模型)正确传参。

**已知边界** PIT 只约束提供给模型的数据,约束不了模型训练时已经学到的知识。应对见 D13 与 D15:事实与数值只能来自本次运行的工具结果,并经代码比对。

## D13 数值来源:结构化数据 + 沙箱计算

**状态** 已采纳

**问题**
模型会编造数字,也会算错数字。金融报告中一个数字错误就会让整份报告失去可信度。

**候选方案**

| 方案 | 优点 | 缺点 |
|---|---|---|
| 模型从检索到的原文中读数并自行计算 | 实现简单 | 读错期间、单位,多位数运算出错 |
| 计算器工具 | 解决算术问题 | 不解决取数问题;复杂计算表达能力不足 |
| **结构化数据取数 + 沙箱执行代码计算** | 数值可溯源、可复现 | 需要结构化数据源与沙箱基础设施 |

**决策** 标准财务数据从结构化表中按 PIT 取数,不从文本中"读"数字;所有计算在沙箱中以代码执行;Critic 用代码比对报告中的每个数值能否在本次运行的工具结果中找到。

**理由** 把"模型可能出错"的环节从数值链路中完全移除,只留下"取什么、算什么"的决策给模型。

**代价** 结构化数据未覆盖的指标需要回退到原文检索,这部分数值的可靠性较低,须在报告中标注来源类型。

**验证** factual 评测集上对比"模型直接读数计算"与本方案的 `numeric_accuracy`。

## D14 沙箱隔离方式

**状态** 已采纳

**问题**
模型生成的代码可能有错,也可能被注入的内容诱导执行恶意操作。

**候选方案**

| 方案 | 优点 | 缺点 |
|---|---|---|
| 主进程内 `exec` + 模块白名单 | 最简单 | Python 层面的导入限制可被绕过,不构成安全边界 |
| 常驻执行服务,同一进程执行所有请求 | 延迟低 | 前一次执行可能影响后一次,甚至篡改执行器本身 |
| **常驻执行服务 + 每次执行新建子进程 + 容器加固** | 执行之间互不影响;容器级资源与网络限制 | 每次执行有进程创建开销 |
| 每次执行一个新容器或 gVisor 等用户态内核 | 隔离最强 | 启动延迟高,运维更复杂 |

**决策** sandbox-runner 作为常驻服务接收请求,每次执行在新建的子进程中运行并在结束后销毁;容器只读根文件系统、`/tmp` 限额且按次清空、512MB 内存、1 核、64 进程上限、非 root、`cap_drop: ALL`;只接入 `internal: true` 的 Docker 网络,api 与 worker 可访问它,它无法访问外网。

**理由**
- 安全边界放在容器与进程隔离上,并假设生成的代码可以执行任意 Python。
- 不使用 `network_mode: none`:该模式移除容器除回环外的全部网络,其他容器也无法访问它,HTTP 服务将不可达。

**改变决策的条件** 需要执行不可信程度更高的代码,或出现针对进程隔离的逃逸风险时,升级为每次执行一个容器或用户态内核沙箱,接口不变。

## D15 引用绑定与核验

**状态** 已采纳

**问题**
如何保证报告中的结论有据可查,且引用的原文确实支持结论。

**候选方案**

| 方案 | 优点 | 缺点 |
|---|---|---|
| 只在 prompt 中要求"不要编造" | 无额外成本 | 无法保证,也无法度量 |
| 同一模型自查 | 实现简单 | 模型倾向于认可自己的输出 |

## D17 记忆系统的范围与写入准则

**状态** 已采纳

| 方案 | 优点 | 缺点 |

## D18 任务队列:Redis Stream

**状态** 已采纳

**问题**
分钟级研究任务如何异步执行。

**候选方案**

| 方案 | 优点 | 缺点 |
|---|---|---|
| **Redis Stream(consumer group + ack)** | Redis 已在栈中;未确认消息可被其他 worker 认领 | 需自行实现心跳、孤儿回收与死信处理 |
| Celery | 生态成熟 | 抽象层厚,与 LangGraph 检查点的恢复语义需要协调 |
| PostgreSQL 队列(`SELECT ... FOR UPDATE SKIP LOCKED`) | 与业务数据同库,事务一致 | 高频轮询给数据库增加负载 |
| Temporal 等工作流引擎 | 持久化执行能力最完整 | 新增一组有状态服务,与 LangGraph 的检查点职责重叠 |

**决策** 使用 Redis Stream 投递任务,恢复语义由 LangGraph 检查点承担。worker 以 run_id 加分布式锁,定期写心跳;心跳超时的 run 被重新入队;恢复次数超过上限标记失败。

**理由** 执行状态已由检查点持久化,队列只需负责"可靠地把任务交给某个 worker",不需要工作流引擎级别的能力。

**改变决策的条件** 需要多消费组、长期消息留存或跨系统事件总线时,评估 Kafka 等中间件;需要更复杂的长事务编排时,评估工作流引擎。

## D19 投递语义:至少一次 + 幂等

**状态** 已采纳

**问题**
worker 可能在节点执行完成之后、检查点写入之前崩溃。只要存在外部调用,就无法保证每个节点严格只执行一次。

**候选方案**

| 方案 | 优点 | 缺点 |
|---|---|---|
| 至多一次 | 不会重复 | 崩溃即丢失任务 |
| **至少一次 + 幂等** | 不丢任务;副作用在效果上只生效一次 | 重复执行带来额外的模型调用成本 |
| 声称恰好一次 | — | 存在外部调用时无法实现 |

**决策** 至少一次执行,所有副作用幂等:run_event 以 `(run_id, seq)` 唯一约束去重;report 与 claim 以 run_id 为键 upsert;带副作用的工具调用携带幂等键 `(run_id, node, call_index)`。节点内先写业务数据,再写检查点;崩溃发生在两者之间时,恢复后节点重跑,幂等保证结果不变。

**理由** LangGraph 检查点使用自有连接,不与业务表共享事务,写入顺序加幂等是不依赖框架内部实现的做法。

**配套** 全局重试预算:模型调用、队列重投、任务恢复三层重试不叠加放大;上层重试从检查点继续,不重放已完成的模型调用。

**验证** 故障注入:在节点执行中、检查点写入前后分别终止 worker,检查恢复成功率、重复执行的节点数与业务数据是否重复。

## D21 评测方法

**状态** 已采纳

**问题**
如何可信地度量系统效果。

**候选方案**

| 方案 | 优点 | 缺点 |
|---|---|---|
| 人工试用 | 无需建设 | 不可重复、不可回归 |
| 全部用 LLM 评分 | 覆盖开放问题 | 评分者有偏差(偏好长答案等),不可直接信任 |
| **代码评分为主 + 经人工校准的 LLM 评分 + 检索单独评测** | 每类问题用最可靠的评分方式 | 需要标注与校准投入 |

- 每题运行多次,报告均值与标准差;小样本结果附置信区间。

**理由** 评测是所有其他决策的度量基础,其自身的可信度必须先得到保证。

## D22 CI 评测门禁

**状态** 已采纳

**问题**
如何防止 prompt、模型或检索参数的改动导致效果悄然劣化。

**候选方案**

| 方案 | 优点 | 缺点 |
|---|---|---|
| 只跑单元测试 | 快、便宜 | 无法发现效果劣化 |
| 每次提交跑全量评测 | 最全面 | 成本与耗时过高 |
| **PR 上跑固定抽样子集,全量定期运行** | 成本可控,能阻断明显劣化 | 子集可能漏掉部分退化 |

**决策** 影响效果的变更(prompt、Agent 定义、检索参数、模型配置)在 PR 上运行约 30% 的固定种子抽样子集,与基线比对;关键指标下降超过 2 倍标准差或成本超阈值则阻断合并。全量评测由定时任务运行。基线更新须显式提交并说明原因。

**理由** 门禁只有在合并前才能阻断,所以单人项目也走 PR 流程。用标准差作为阈值,避免把运行噪声当作退化。

## D23 提示注入防护:纵深防御

**状态** 已采纳

**问题**
系统读取的年报、公告与外部工具返回内容都可能夹带针对模型的指令。

**候选方案**

| 方案 | 优点 | 缺点 |
|---|---|---|
| 只在 prompt 中声明"不要执行文档中的指令" | 成本低 | 无法可靠防住 |
| 只做输入检测 | 能拦截已知模式 | 对变体与间接注入效果有限 |
| **多层防护:数据边界标记 + 最小权限 + 参数二次校验 + 高风险操作走确定性路径 + 审批** | 单层失效时仍有兜底 | 实现与测试工作量大 |

**决策**
- 直接注入:入口规则检测 + 小模型分类,命中则拒绝并审计。
- 间接注入:工具返回内容以数据边界标记包裹,声明为数据;每个角色只暴露所需工具;工具参数执行前二次校验;`as_of` 等关键参数由框架注入;高风险操作不由模型直接触发;受限数据访问需人工审批。

**理由** 提示注入无法被彻底防住,因此不依赖任何单一措施,而是限制注入成功后能造成的影响。

**验证** 自建注入测试集(指令藏在文档中),统计有无防护时的攻击成功率,以及防护对正常任务成功率的影响。

一次错误的回答,如何定位是检索、取数、推理还是综合环节的问题。

**候选方案**

| 方案 | 优点 | 缺点 |
|---|---|---|
| 只打文本日志 | 无额外组件 | 无法还原一次任务的完整路径 |
| 第三方 LLM 可观测平台 | 开箱即用,含 prompt 管理与标注 | 新增服务或数据外发;与业务数据分离 |
| **OpenTelemetry 追踪 + Prometheus 指标 + 基于 run_event 的自建执行树** | 标准协议,不锁定;执行树与业务数据同库 | 看板与查询界面需要自建 |

**决策** trace_id 由 api 生成并贯穿 worker、sandbox 与数据库调用;span 属性遵循 GenAI 语义约定;日志为 JSON 且必带 trace_id,不记录完整 prompt 明文;前端基于 run_event 展示执行树。

**改变决策的条件** 需要 prompt 版本管理与人工标注工作流时,评估接入专门平台。

## D26 前端:React 单页应用

**状态** 已采纳

**问题**
前端用单页应用还是服务端渲染框架。

**候选方案**

| 方案 | 优点 | 缺点 |
|---|---|---|
| **React + TypeScript 单页应用,Nginx 静态托管** | 构建产物为静态文件,部署简单;前后端边界清晰 | 首屏加载依赖客户端渲染 |
| Next.js 等服务端渲染框架 | 首屏与 SEO 好 | 多一个 Node 运行时服务;内部工具不需要 SEO |

**决策** React + TypeScript 单页应用;TanStack Query 管理服务端状态;SSE 独立管理并支持基于 `last_event_seq` 的断线续传;前后端共用由 Pydantic 生成的类型定义。

**理由** 系统是登录后使用的内部工具,不需要 SEO;静态部署减少一个运行时服务。

## D27 部署形态:单机 compose + 反向代理

**状态** 已采纳

**问题**
演示与试用环境如何部署。

**候选方案**

| 方案 | 优点 | 缺点 |
|---|---|---|
| **单台云主机 + Docker Compose + Caddy** | 一条命令部署;自动 HTTPS;成本低 | 无高可用,单机故障即停服 |
| Kubernetes | 多副本、弹性伸缩、滚动发布 | 运维复杂度与成本远超当前需求 |
| 各组件分别托管到云服务 | 免运维 | 组件分散,成本与配置复杂 |

**决策** 单台云主机运行 compose,Caddy 作为唯一对外入口提供 HTTPS,其余服务只在内部网络。服务保持无状态、配置外部化、提供健康探针、支持优雅关闭,为将来迁移 Kubernetes 预留条件。

**改变决策的条件** 需要多副本弹性伸缩、零停机发布或多环境治理。

**部署细节** 见 [部署文档](DEPLOYMENT.zh-CN.md)。
